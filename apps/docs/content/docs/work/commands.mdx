All Agile functionality lives under one namespace. Every command accepts `--json` for agents.

```bash
agileflow work init
agileflow work new epic|story|decision --title "..."
agileflow work list
agileflow work show <id>
agileflow work status <id> <status>
agileflow work board
agileflow work next
agileflow work evidence <story> [--criterion <n> --kind test --ref <ref>]
agileflow work import v4 --preview
```

There is no `work delete` (set `status: cancelled` to keep history) and no `work doctor`: `agileflow check` validates the workspace.

## work init

```bash
agileflow work init                 # docs/agile
agileflow work init --root planning # another directory
agileflow work init --no-skills     # workspace and CLI only
agileflow work init --yes           # no questions (adopts a compatible existing workspace)
agileflow work init --json          # machine-readable result
```

```text
AgileFlow Work organizes durable product work using:
  product
  roadmap
  epics
  stories
  decisions
Workspace:
  docs/agile
Install Agile workflow skills?
  [x] creating-epics
  [x] writing-stories
  [x] working-story
  [x] reviewing-story
Continue? yes
```

It adds `work: { enabled: true, root: docs/agile }` to `agileflow.yaml` (creating it if needed), creates `README.md`, `00-product/product.md`, and `01-roadmap/roadmap.md`, and installs the `agile` pack (including `recording-decisions`) unless you decline. If Git ignores the workspace directory (for example a `/docs/` rule in `.gitignore`), or only part of it (say `docs/agile/03-stories/`), `work init` warns, names the exact ignored path, and names the rule: work items only help a team when they are committed. `work new` and `agileflow check` give the same warning. `work init` runs under the same project lock as other changing commands, so it waits for (or clearly refuses next to) a concurrent `add` or `update`. `agileflow init` offers the same setup ("Enable AgileFlow Work?").

If the directory already exists, nothing is overwritten. A compatible workspace is adopted after confirmation (`--yes` confirms); an incompatible one (unexpected folders such as `09-agents/`, subfolders in `03-stories/`, unreadable artifacts) is explained and left untouched, and the command exits `1`. Running `work init` again recreates missing starter files without touching the others.

## work new

```bash
agileflow work new epic --title "Social authentication" --horizon now --priority p1
agileflow work new story --epic 7M4K --title "Add Google sign-in"
agileflow work new story --title "Fix duplicate invoice email"          # standalone
agileflow work new story --title "Account linking" --depends-on 3Q7M
agileflow work new decision --title "Use Auth.js" --related 7M4K
```

```text
Created STORY-3Q7MX2PK
docs/agile/03-stories/STORY-3Q7MX2PK-add-google-sign-in.md
```

With `--json`: `{"id": "STORY-3Q7MX2PK", "type": "story", "path": "docs/agile/03-stories/...", "warnings": []}`. New items start as `proposed` (epics, decisions) or `backlog` (stories) unless `--status` says otherwise. References must exist. Titles must be one line without control characters (terminal escape sequences, tabs, bells are refused). If Git would ignore the new file, a warning names it and the matching `.gitignore` rule.

## work list

```bash
agileflow work list
agileflow work list --type epic          # grouped by horizon
agileflow work list --status ready
agileflow work list --epic 7M4K
agileflow work list --status ready --json
agileflow work list --ready              # stories that can start now
agileflow work list --type stories       # singular or plural
```

If two files use the same ID, `list` and `board` show both, mark them `(duplicate ID)`, and warn on stderr naming the files; `--json` adds `"duplicateId": true` to those items (and `board --json` a `duplicates` list). Commands that change an item refuse duplicate IDs instead of picking one.

`--ready` lists stories that are `ready` or `backlog` and whose every `depends_on` story is `done`. Each story in `--json` output carries its derived readiness:

```json
{
  "id": "STORY-3Q7MX2PK",
  "type": "story",
  "title": "Add Google sign-in",
  "status": "ready",
  "path": "docs/agile/03-stories/STORY-3Q7MX2PK-add-google-sign-in.md",
  "priority": "p1",
  "epic": "EPIC-7M4K2P9Q",
  "depends_on": ["STORY-T9K2P4VC"],
  "acceptanceCriteria": { "total": 4, "checked": 0 },
  "dependenciesDone": false,
  "waitingOn": ["STORY-T9K2P4VC"],
  "ready": false
}
```

## work show

```bash
agileflow work show 3Q7M
agileflow work show 3Q7M --body          # also print the Markdown
```

```text
STORY-3Q7MX2PK
Add Google sign-in
Status:    ready
Priority:  p1
Epic:      EPIC-7M4K2P9Q  Social authentication
Dependencies:
  none
Acceptance Criteria:
  2 / 4 checked; evidence: 1 verified, 1 stale, 2 not verified
  [x] 1. Google appears as an authentication option.  (verified)
         test test/auth.test.ts::shows google (at 3bb3348b, 2026-09-29)
  [x] 2. A new Google user can create an account.  (stale)
         test test/auth.test.ts:88 (at 3bb3348b, 2026-09-28); changed since: src/auth/google.ts
  [ ] 3. An existing user can link Google.  (not verified)
  [ ] 4. Errors are shown in the sign-in form.  (not verified)
Path:      docs/agile/03-stories/STORY-3Q7MX2PK-add-google-sign-in.md
```

Each criterion shows its evidence status (see [work evidence](#work-evidence)). A checked box alone is never shown as verified: a checked criterion without evidence reads `not verified: checked, no evidence`. `--json` adds an `evidence` object with `counts` and per-criterion `status` and `records`.

A story also lists the stories that depend on it ("Needed by") and the decisions that reference it. For an epic it derives the stories (grouped by status), related decisions, and progress. For a decision it lists the related items.

## work status

```bash
agileflow work status 3Q7M in-progress
```

```text
STORY-3Q7MX2PK
ready -> in-progress
```

Only the `status:` line changes; the rest of the file stays byte-for-byte identical. The file is written atomically (temporary file, then rename), and only if its content hash still matches what the command read: if another agent or an editor changed it in the meantime, nothing is written and the command asks you to run it again. Closing an epic also re-reads its stories (including story files created since) before deciding. Invalid values are rejected. Moves outside the recommended flow, marking a story done with unchecked criteria, and starting a story whose dependencies are not done are allowed with a warning. Closing an epic with unfinished stories is refused unless you pass `--force` (cancel the stories you do not intend to finish instead).

## work next

```bash
agileflow work next                  # top 5
agileflow work next --limit 10 --epic 7M4K
agileflow work next --explain        # also why the top other stories are not eligible
agileflow work next --json
```

```text
Next (2 of 2 eligible)
  1. STORY-3Q7MX2PK  p1  Add Google sign-in
     status is ready, priority p1; every dependency is done (STORY-T9K2P4VC); epic EPIC-7M4K2P9Q is active, horizon now
  2. STORY-Q6M2J7NK  p2  Fix invoice email
     status is ready, priority p2; no dependencies

Nothing was assigned or started. Start one with `agileflow work status <id> in-progress`.
```

A story is eligible when its status is `ready`, every `depends_on` story exists and is `done`, its epic (if any) is not done or cancelled, and its ID is not duplicated. Order: priority (`p0` first, unset last), then the epic's horizon (`now`, `next`, `later`, none), then how many open stories it unblocks, then title. `--explain` lists the highest-priority stories that are not eligible and why (`waiting on STORY-... is in-progress`, `status is backlog: refine it and set it to ready first`, ...). It is read-only: it never assigns, starts, or changes anything.

## work evidence

```bash
agileflow work evidence 3Q7M                                   # per-criterion status
agileflow work evidence 3Q7M --criterion 1 --kind test --ref "test/auth.test.ts::shows google" --file src/auth/google.ts
agileflow work evidence 3Q7M --criterion "link Google" --kind pr --ref https://github.com/acme/app/pull/42 --note "reviewed by Sam"
agileflow work evidence 3Q7M --criterion 4 --kind manual --ref "tried a wrong password in the preview build"
```

Records evidence for one acceptance criterion: `--criterion` is its number (1-based) or its text (or an unambiguous part of it); `--kind` is `test`, `inspection`, `pr`, or `manual`; `--ref` is a test name or `file:line`, an inspected `file:line`, a PR URL, or what was checked by hand; `--note` is optional. The command stores the current Git commit and a content hash of the files the evidence depends on: the file in `--ref` (for `test` and `inspection`) and every `--file`. Paths are relative to the current directory (the `--ref` file falls back to the project root) and are stored relative to the project root, so the record means the same file in every clone; paths or symlinks that lead outside the project are refused. When one of those files changes, the evidence shows as **stale**. Evidence without hashed files (a PR, a manual check) cannot go stale automatically; add `--file` for the code it covers.

Recording again with the same criterion, kind, and ref refreshes that record; anything else is added. Only the story's evidence block changes: the checkbox and the status are left alone, the write is atomic, and it is refused if the story changed since it was read. The format is described in [Artifacts](/work/artifacts#acceptance-criteria-evidence).

## work import v4

```bash
agileflow work import v4 --preview                 # show the plan, write nothing
agileflow work import v4 --yes                     # import
agileflow work import v4 --yes --prefer markdown   # also import items whose files disagree, using the Markdown values
```

```text
Import the v4 backlog into docs/agile/
Read: docs/09-agents/status.json, docs/06-stories (never changed)
Stories (2 new)
  V4       NEW ID          V4 STATUS  STATUS  PRIORITY  EPIC     DEPENDS ON  TITLE
  US-0001  STORY-8K2M4Q7T  completed  done    p1        EP-0001  -           Welcome screen
  US-0002  STORY-D3V9N6XA  todo       ready   -         EP-0001  US-0001     Tour
Remapped values (v4 -> Work)
  story status: completed -> done  (1: US-0001)
  story status: todo -> ready  (1: US-0002)
Held back (1): status.json and Markdown disagree, or the item is ambiguous
  US-0003  status: status.json "done", Markdown "in progress"
  Nothing is guessed. Fix the v4 files so they agree, or rerun with --prefer json or --prefer markdown.
```

Converts a v4 backlog (`docs/05-epics/`, `docs/06-stories/`, and `docs/09-agents/status.json`) into Work epics and stories. The preview shows every mapping: the v4 status next to the new one, priorities, epic and dependency links (as v4 IDs), and a list of remapped values (`todo -> ready`, `High -> p1`, ...). The new IDs are derived from the v4 IDs, so the preview shows exactly the IDs the import writes.

- **Conflicts are not guessed.** When `status.json` and the Markdown file disagree on status, title, priority, or epic, the item is held back and listed with both values. Fix the v4 files, or choose a side for every conflict with `--prefer json` or `--prefer markdown` (the choice is reported). Items claimed by two Markdown files, or that refer to a v4 ID more than one Work item already carries (a duplicate `legacy_id`), are always held back. Links to held-back items are kept and resolve once they are imported.
- **Provenance is kept.** Each imported item records its v4 ID in `legacy_id` and the files it came from in `legacy_source`. Running the import again skips imported items and repeats no notes about them.
- **Bodies are cleaned, not rewritten.** Stale `**Status**: ...` lines are removed (the frontmatter status is authoritative) and terminal escape sequences are stripped; everything else is kept as written.
- **The v4 files are never changed or deleted.** Remove them yourself once you are happy with the result. `agileflow migrate v4` and `agileflow check` point to `agileflow work import v4 --preview` while a v4 backlog has items that are not imported.

## Integrating with agent orchestrators

Agile Work is not an orchestrator and does not run agents. Multi-agent tools (a Kanban of agents, parallel worktrees, a CI bot) can drive it through the JSON interface:

1. `agileflow work list --ready --json` returns the stories an agent can pick up now.
2. The orchestrator assigns a story and moves it: `agileflow work status STORY-... in-progress --json`.
3. The agent works the story (the `working-story` skill), then `in-review`; `reviewing-story` checks every criterion before `done`.
4. `agileflow work board --json` gives the whole picture, including stories marked ready whose dependencies are unfinished.

IDs are random (`STORY-` plus 8 Crockford Base32 characters), so parallel agents on different branches can create items without coordinating. Collisions are astronomically unlikely, and `agileflow check` reports duplicate IDs as errors if one ever happens (for example after copying a file).

`agileflow work next --json` gives the same queue ranked, with the reasons; it never assigns anything. Evidence recorded with `agileflow work evidence` lets a reviewer (or `reviewing-story`) see which criteria are verified, stale, or not verified.

In `--json` mode every `work` command prints exactly one JSON document on stdout, including usage errors such as a missing `--title` or an unknown option (no help text is printed then). Errors are `{"ok": false, "error": {"code": "...", "message": "...", "hints": [...]}}` with exit code `1`; `code` is `usage` for invalid usage and `error` for Work errors, as for every other command.

`work new`, `work status`, `work evidence` (when recording), and `work import` run under the same project lock as other changing commands and scan the workspace inside it, so concurrent commands (for example parallel agents) never lose each other's changes.

## Validation in agileflow check

When Work is enabled, `agileflow check` adds a section:

```text
Agile Work
  [ok] workspace structure valid
  [ok] 4 epics
  [ok] 23 stories
  [ok] 3 decisions
  [ok] no duplicate IDs
  [ok] no missing epic references
  [ok] dependency graph valid
  [!] STORY-A72D... is marked ready but depends on STORY-M88Q... (in-progress)
Result: healthy with 1 warning
```

Errors (the check fails): duplicate IDs, invalid frontmatter or unknown statuses, unknown epic, dependency, or decision references, dependency cycles, and epics marked done with unfinished stories. Warnings: done stories with unchecked acceptance criteria, ready stories with unfinished dependencies, IDs mentioned in a body that do not exist, evidence blocks that do not parse or point at criteria that no longer exist, fields outside schema 1, files that do not belong in the workspace, and workspace paths Git ignores (naming the exact path and rule). While a v4 backlog has items that are not imported, an info line points to `agileflow work import v4 --preview`. Long dependency cycles are shortened to their first IDs plus `... (N more)`, and titles or criteria are printed without control characters. `check` never changes a status.
